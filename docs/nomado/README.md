# Номадо: переориентация с travel-торговли на маркетплейсы

Статус: **черновик v1**, собран без доступа к текущему коду Номадо и к серверам
(см. «Чего я не видел» в конце). Всё, что помечено `‹уточнить›`, — допущение,
которое надо подтвердить или поправить одной строкой.

---

## 1. Что меняется, а что нет

Номадо — это не сайт и не один репозиторий, а **связка «два VPS + агенты в Telegram»**.
Переориентация бьёт только по верхнему слою — по предметной области. Инфраструктура,
на которой всё стоит, к домену бизнеса безразлична.

| Слой | Travel-торговля (сейчас) | Маркетплейсы (цель) | Переделка |
|---|---|---|---|
| Хостинг | 2 × VPS Start (Финляндия), 1289 ₽/мес | без изменений | нет |
| Транспорт | Telegram → Claude Code (`dashi-channel`) | без изменений | нет |
| Память агента | `core/hot/recent.md` + `verbose-*.jsonl` | без изменений | нет |
| Safety / redact | редактор секретов + HTML-валидатор | без изменений | нет |
| **Воркспейс агента** | travel-промпт, travel-данные | промпт и данные по маркетплейсам | **полная замена** |
| **Слой данных** | ‹уточнить: что за travel-данные› | товары, цены, поставки, реклама, отзывы | **новый** |
| **Внешние API** | ‹уточнить: GDS / партнёрки?› | WB Seller API, Ozon Seller API | **новый** |
| Домен | `nomadotravel.com` | ‹уточнить: оставляем или переезжаем› | решение за вами |

Вывод, который стоит зафиксировать до начала работы: **платформу переписывать не нужно.**
Плагин `dashi-plugin-claude-code` — предметно-нейтральный транспорт. Переориентация Номадо =
новый воркспейс агента + новый слой данных + коннекторы к маркетплейсам. Это недели работы,
а не месяцы, и старый travel-воркспейс можно просто оставить рядом, не удаляя.

## 1a. Две линии бизнеса, а не одна

Кабинета сейчас два: **свой и один клиентский**, ведутся одинаково.

| Линия | Что это | Во что упирается |
|---|---|---|
| Своя торговля | собственный товар, свои закупки и риск | деньги: рост = закупка = замороженный капитал |
| Услуги селлерам | ведение чужих кабинетов | время: рост = ещё один кабинет руками |

Выбирать между ними на двух кабинетах рано, и мы не выбираем. Из этого следуют
два решения:

1. **Строим общее ядро** — юнит-экономику, импорт выгрузок, алерты. Оно нужно обеим
   линиям одинаково. Клиентская машинерия (онбординг, разграничение доступа,
   дашборд по N клиентам) откладывается: сейчас это работа впрок.
2. **Многокабинетность закладывается сразу**, но без церемоний: каталог на кабинет
   и запрет смешивать данные. Стоит дёшево, а переделывать структуру данных
   на пятом клиенте дорого.

Что стоит держать в голове: агенты дают рычаг там, где узкое место — время.
В услугах одна и та же работа повторяется × N клиентов, поэтому снятая рутина
умножается. В своей торговле агент считает лучше, но капитала в обороте от этого
не прибавляется — главное ограничение он не расшивает.

### Разница, которая есть даже при одинаковом ведении

Она не в процессе, а в том, откуда берётся доход:

| | Свой кабинет | Клиентский |
|---|---|---|
| Наш доход | маржа с товара | гонорар |
| Чья прибыль считается | наша | клиента — за это нам платят |
| Что ещё надо считать | — | **нашу ставку часа**: гонорар ÷ потраченные часы |

Ставка часа — единственная цифра, которая отличает работу от подработки, и её
обычно не считает никто, пока не станет поздно. Сравнивать её нужно не с зарплатой,
а с тем, сколько принесли бы те же часы, вложенные в свой кабинет. Поля под это
есть в `accounts/_template/profile.md`.

### Изоляция данных

Каждый кабинет — свой каталог `core/accounts/<slug>/`, и агенту прямо запрещено
смешивать их в одном ответе. Это не педантизм: цифры клиента, всплывшие в разговоре
про другого клиента, — это потеря обоих.

**Если клиент получит доступ к боту** — ему нужен отдельный бот и отдельный
workspace. Плагин изолирует по процессу: один агент = один бот = один workspace =
один allowlist. «Разграничение по ролям внутри одного бота» надёжным не будет:
агент видит все файлы, до которых дотягивается.

Каталог `accounts/` живёт только на сервере. В репозитории — пустой `_template/`,
на остальное стоит гард в `.gitignore`.

## 2. Два агента, а не один

Один процесс плагина = один агент = один Telegram-бот. Задачи делятся естественно,
и смешивать их в одном боте вредно: у экономики и у контента разные данные, разный
тон и разная цена ошибки.

### `nomado-market` — деньги

1. **Юнит-экономика до закупки.** Маржа с учётом комиссии, логистики, хранения,
   налога и процента выкупа. Ответ на «заходить или нет» — цифрой.
2. **Рентабельность.** По каждой карточке и по магазину целиком, с отдельным
   списком убыточных позиций: в общей сводке они не видны, а прибыль съедают.
3. **Цена.** Коридор: пол по своей экономике, потолок по вилке конкурентов,
   рекомендация под выбранную стратегию (`core/pricing-strategy.md`).
4. **Разбор ниши.** Вилка цен, плотность, требуемая оборачиваемость.
5. **Сводка и алерты.** Что заканчивается, что встало, что с рекламным счётом.

### `nomado-content` — карточки

1. **Разбор визуала** по чек-листу: читается ли первое фото в плитке выдачи,
   не спорит ли инфографика с товаром, есть ли масштаб.
2. **Сравнение с конкурентами** по присланным скриншотам и выгрузкам.
3. **Тесты** — последовательные, с журналом: одна гипотеза за раз, период
   не короче двух недель, отрицательный результат записывается наравне с
   положительным.
4. **Тексты**: заголовок, характеристики, описание.
5. **Отзывы и вопросы.** Отзыв пишется для будущих покупателей, а не для автора;
   вопрос — для того, кто сомневается прямо сейчас. Повторяющийся вопрос — дыра
   в карточке, он уходит в `core/faq-gaps.md` и чинится характеристиками или фото.

### Чего они не делают

Ставки, аналитику по кабинетам и разбор конкурентов из выдачи закрывает **Bider** —
см. раздел 4a. Агенты его не дублируют.

## 4a. Реклама: Bider остаётся, агент за ним смотрит

**Bider** (v.421.13) — покупная десктопная программа на ноутбуке, и это не только
биддер: он агрегирует все кабинеты, к которым есть доступ, даёт аналитику и разбор
конкурентов.

Отсюда решение: **не дублировать его ни в ставках, ни в аналитике.** Свой биддер
будет драться с ним за ставки в одном кабинете. Свой сбор данных потребует токена
на каждый кабинет и даст худшую копию того, что уже куплено. Конкурентов агент
вообще не увидит — в WB API их нет.

Разделение ролей:

| Кто | Что делает | Где работает |
|---|---|---|
| Bider | ставки, аналитика по кабинетам, конкуренты | ноутбук, только когда открыт |
| Агент | надзор, сводки, алерты | сервер, круглосуточно |

Ключевая разница: **Bider показывает, когда в него смотрят. Агент приходит сам.**
Счёт в нуле два месяца — ровно эта дыра.

**Источник данных — экспорт в Excel, он в Bider есть.** Токены WB API на старте не
нужны вовсе: `scripts/bider-ingest.py` разбирает выгрузку в CSV прямо в каталог
кабинета, агент читает их как обычные файлы. Это снимает главную проблему
многокабинетной схемы — иначе токен понадобился бы на каждый клиентский кабинет,
и каждый пришлось бы выпрашивать у клиента.

API продвижения WB (категория «Продвижение») остаётся на потом — он нужен, только
если захочется, чтобы агент сам менял ставки. Пока Bider это делает, не нужен.

Ловить агент должен то, чего Bider не сообщает:

- рекламный счёт опустел или близок к нулю;
- кампании не менялись N дней — то есть биддер не работает (ноутбук выключен,
  программа закрыта, подписка истекла);
- бюджет открутился быстрее обычного;
- ДРР вышел за порог;
- дубли кампаний на одном SKU.

### Состояние на 31.08.2026 (по скриншотам Bider)

**Два блокера, и оба важнее любой автоматизации:**

1. **Истёк API-токен WB.** Bider пишет об этом в статусной строке: «У API-токена
   истек срок действия. Удалите его из приложения или Создайте новый API-токен».
   Пока токен мёртв, Bider не синхронизируется, и всё, что он показывает по
   рекламе, — это последние успешно полученные данные, а не текущее положение дел.
   Отсюда «59 дн. назад» на ставках, нулевой счёт и прочерки в затратах и CTR.
   **Выводы по рекламе до перевыпуска токена делать нельзя** — неизвестно, стоят
   кампании или просто не читаются.
2. **Второй магазин без лицензии Bider.** «Обработан ограниченный объем данных.
   Необходима лицензия на приложение для этого магазина». По нему картина заведомо
   неполная — решение о лицензии принимать до того, как строить на этих данных
   отчётность.

Порядок действий: перевыпустить токен → синхронизировать → и только потом смотреть,
что на самом деле с рекламой.

### Что известно про ассортимент

- Два магазина, оба на WB: свой и клиентский (соответствуют `accounts/`).
- 166 карточек из 327 в текущем фильтре.
- Категории: бижутерия и украшения (колье, серьги, комплекты), солнцезащитные очки,
  одежда (брюки).
- Почти всё помечено «РАСПРОДАЖА», скидки 31–41%. Значит **реальная цена продажи
  на треть ниже витринной**, и юнит-экономику надо считать по ней, а не по цене
  до скидки. Это типовая ошибка, которая превращает расчёт маржи в фантазию.
- Ставки в кампаниях проставлены (90–377 ₽), но бюджеты по большинству нулевые.
  Проверять после перевыпуска токена.

На одной карточке бывает несколько типов кампаний сразу — Аукцион, CPC, Uni.
Это не дубли, а разные механики; агент не должен считать их повтором.

### Данные по дням — что из них берём

Вкладка «По дням» даёт по каждому SKU: переходы, конверсию в корзину, корзины,
конверсию в заказ, заказы, процент выкупа, выкуплено / в пути / отмены, среднюю
цену, сумму заказов, ДРР и рекламный блок (показы, CTR, клики, цена клика, CPM,
счёт, корзины и заказы с рекламы, включая смежные).

`bider-ingest.py` опознаёт этот лист и пишет рядом с сырым CSV нормализованный:

- числа очищены от `₽`, процентов и неразрывных пробелов;
- `~?~` превращается в пустое значение, а **не в ноль** — это «ещё неизвестно»
  (заказ не доехал), и ноль здесь исказил бы выкуп;
- даты в ISO;
- добавлены два поля, которых в выгрузке нет: сквозная конверсия перехода в заказ
  и выручка на переход. Смотреть надо на них — промежуточные конверсии по
  отдельности обманчивы.

Колонки маппятся по позиции, а лист опознаётся по словам «Переходы», «Ср. цена»,
«Сум. заказы»: в заголовках Bider стоят эмодзи со скин-тонами, и совпадение по ним
ломалось бы от версии к версии. Лишние колонки не теряются — уходят в `extra_N`.

**Про объёмы.** На реальных данных карточки — 48–62 перехода в день. При таких
числах дневная конверсия в корзину скачет от 2% до 12%, и это шум, а не поведение
покупателей: разница между 1 корзиной и 7. Практическое следствие — ни решения по
цене, ни выводы теста по одному дню не принимаются. Минимальное окно — две недели,
как и записано в журнале тестов контент-агента.

## 4b. Масштаб: как выбирать, с чем работать

Сейчас карточек 327 и магазина два. Когда станет больше, узким местом станет не
анализ, а **выбор**: с чего начать сегодня. Правила описаны в
`core/triage.md` воркспейса и сводятся к трём вещам:

- считаем не «плохо/хорошо», а **рубли на столе в месяц** — только так позиции
  сравнимы между собой и между магазинами;
- сначала утекающие деньги (работаем в минус, замороженный остаток), потом
  упущенные (трафик есть — карточка не продаёт; продаёт — не видят);
- выдаём **не больше пяти позиций**, у каждой одно действие и оценка уверенности.

Между магазинами: обязательства вперёд денег — у клиентского кабинета есть сроки
отчётности, у своего нет; дальше по сумме на столе.

Отдельно прописано, **когда молчать**: данных меньше двух недель, переходов меньше
30 в день, выгрузка старше недели, истёкший токен или магазин без лицензии.
Уверенный список, посчитанный по шуму, вреднее пустого ответа — по нему примут
решения.

### Как данные попадают к агенту

Подключаться к окну Bider не нужно и не следует: такая связка ломается от любого
обновления программы и не логируется. Путь проще и надёжнее:

```
Bider → экспорт в Excel → папка на ноутбуке
      → синхронизация (Яндекс.Диск / Syncthing / rclone)
      → сервер → bider-ingest.py → data/<кабинет>/
      → агент считает и пишет в Telegram
```

С вашей стороны — один клик на экспорт. Всё остальное происходит само, и работает,
даже когда ноутбук выключен: сервер уже держит последнюю выгрузку.

## 5. Этапы

| Этап | Что делаем | Результат |
|---|---|---|
| 0 | Поднять `nomado-market` из шаблона | Бот отвечает по экономике |
| 1 | Завести кабинеты в `core/accounts/`, заполнить ставки | Маржа считается по каждому кабинету |
| 2 | Первая выгрузка из Bider через `bider-ingest.py` | Агент работает на реальных числах |
| 3 | Занести ассортимент и стратегии | Рекомендации по цене по вашим SKU |
| 4 | Поднять `nomado-content` | Визуал, тексты, отзывы и вопросы |
| 5 | Регулярный импорт выгрузок + алерты | Сводки приходят сами |
| 6 | Решение по travel-контуру | Освобождается сервер или нет |

Развернуть воркспейсы:

```bash
./scripts/nomado-workspace-init.sh                  # экономика
./scripts/nomado-workspace-init.sh --role content   # контент
```

Загрузить выгрузку:
