(см. «Чего я не видел» в конце). Всё, что помечено `‹уточнить›`, — допущение,

## 1. Что меняется, а что нет

Номадо — это не сайт и не один репозиторий, а **связка «два VPS + агенты в Telegram»**.
Переориентация бьёт только по верхнему слою — по предметной области. Инфраструктура,
на которой всё стоит, к домену бизнеса безразлична.

| Слой | Travel-торговля (сейчас) | Маркетплейсы (цель) | Переделка |
|---|---|---|---|
| Хостинг | 2 × VPS Start (Финляндия), 1289 ₽/мес | без изменений | нет |
| Транспорт | Telegram → Claude Code (`dashi-channel`) | без изменений | нет |
| Память агента | `core/hot/recent.md` + `verbose-*.jsonl` | без изменений | нет |
| Safety / redact | редактор секретов + HTML-валидатор | без изменений | нет |
| **Воркспейс агента** | travel-промпт, travel-данные | промпт и данные по маркетплейсам | **полная замена** |
| **Слой данных** | ‹уточнить: что за travel-данные› | товары, цены, поставки, реклама, отзывы | **новый** |
| **Внешние API** | ‹уточнить: GDS / партнёрки?› | WB Seller API, Ozon Seller API | **новый** |
| Домен | `nomadotravel.com` | ‹уточнить: оставляем или переезжаем› | решение за вами |

Вывод, который стоит зафиксировать до начала работы: **платформу переписывать не нужно.**
Плагин `dashi-plugin-claude-code` — предметно-нейтральный транспорт. Переориентация Номадо =
новый воркспейс агента + новый слой данных + коннекторы к маркетплейсам. Это недели работы,
а не месяцы, и старый travel-воркспейс можно просто оставить рядом, не удаляя.

## 1a. Две линии бизнеса, а не одна

Кабинеты в Bider — **и свои, и клиентские**. Значит Номадо после переориентации —
это не «магазин на маркетплейсах», а две линии сразу:

| Линия | Что это | Чем меряется |
|---|---|---|
| Своя торговля | собственный товар, свои закупки и риск | маржа, оборачиваемость |
| Услуги селлерам | ведение чужих кабинетов | стоимость часа, удержание клиента |

Они конфликтуют за одно и то же время, поэтому решение, какая из них главная,
принимать придётся. Но инструменты у них общие: и там, и там нужны юнит-экономика,
карточки, надзор за рекламой. Поэтому агенты строятся многокабинетными с самого
начала — переделывать это потом дороже, чем заложить сейчас.

### Изоляция данных

Каждый кабинет — свой каталог `core/accounts/<slug>/`, и агенту прямо запрещено
смешивать их в одном ответе. Это не педантизм: цифры клиента, всплывшие в разговоре
про другого клиента, — это потеря обоих.

**Если клиент получит доступ к боту** — ему нужен отдельный бот и отдельный
workspace. Плагин изолирует по процессу: один агент = один бот = один workspace =
один allowlist. «Разграничение по ролям внутри одного бота» надёжным не будет:
агент видит все файлы, до которых дотягивается.

Каталог `accounts/` живёт только на сервере. В репозитории — пустой `_template/`,
на остальное стоит гард в `.gitignore`.

## 2. Два агента, а не один

Один процесс плагина = один агент = один Telegram-бот. Задачи делятся естественно,
и смешивать их в одном боте вредно: у экономики и у контента разные данные, разный
тон и разная цена ошибки.

### `nomado-market` — деньги

1. **Юнит-экономика до закупки.** Маржа с учётом комиссии, логистики, хранения,
   налога и процента выкупа. Ответ на «заходить или нет» — цифрой.
2. **Рентабельность.** По каждой карточке и по магазину целиком, с отдельным
   списком убыточных позиций: в общей сводке они не видны, а прибыль съедают.
3. **Цена.** Коридор: пол по своей экономике, потолок по вилке конкурентов,
   рекомендация под выбранную стратегию (`core/pricing-strategy.md`).
4. **Разбор ниши.** Вилка цен, плотность, требуемая оборачиваемость.
5. **Сводка и алерты.** Что заканчивается, что встало, что с рекламным счётом.

### `nomado-content` — карточки

1. **Разбор визуала** по чек-листу: читается ли первое фото в плитке выдачи,
   не спорит ли инфографика с товаром, есть ли масштаб.
2. **Сравнение с конкурентами** по присланным скриншотам и выгрузкам.
3. **Тесты** — последовательные, с журналом: одна гипотеза за раз, период
   не короче двух недель, отрицательный результат записывается наравне с
   положительным.
4. **Тексты**: заголовок, характеристики, описание.
5. **Отзывы и вопросы.** Отзыв пишется для будущих покупателей, а не для автора;
   вопрос — для того, кто сомневается прямо сейчас. Повторяющийся вопрос — дыра
   в карточке, он уходит в `core/faq-gaps.md` и чинится характеристиками или фото.

### Чего они не делают

Ставки, аналитику по кабинетам и разбор конкурентов из выдачи закрывает **Bider** —
см. раздел 4a. Агенты его не дублируют.

## 4. Слой данных

Агент читает и пишет обычные файлы в воркспейсе — никакой БД на старте не нужно:

```
~/.claude-lab/nomado-market/.claude/
├── CLAUDE.md
├── core/
│   ├── hot/recent.md              # память между сессиями (пишет плагин)
│   ├── pricing-strategy.md        # коридор цены и стратегии — общие правила
│   └── accounts/
│       ├── README.md              # реестр кабинетов + правило изоляции
│       ├── _template/             # копируется под каждый новый кабинет
│       ├── own/                   # свой кабинет
│       │   ├── profile.md         # юрлицо, налог, маркетплейсы
│       │   ├── unit-economics.md  # ставки комиссий этого кабинета
│       │   ├── assortment.md      # товары: закуп, цена, остаток, стратегия
│       │   └── suppliers.md
│       └── <клиент>/              # то же самое по каждому клиенту
└── data/
    ├── own/                       # CSV из bider-ingest.py
    └── <клиент>/

~/.claude-lab/nomado-content/.claude/
├── CLAUDE.md
├── core/
│   ├── hot/recent.md
│   ├── visual-checklist.md        # по чему разбирается карточка
│   ├── content-rules.md           # заголовки, описания, ответы
│   ├── test-journal.md            # что тестировали и чем кончилось
│   └── faq-gaps.md                # повторяющиеся вопросы и жалобы
└── data/                          # скриншоты выдачи, выгрузки конкурентов
```

Переход на SQLite имеет смысл, когда позиций станет больше ~200 или понадобится история
цен по дням. До этого файлы читаются агентом целиком и это дешевле во всех смыслах.

## 4a. Реклама: Bider остаётся, агент за ним смотрит

**Bider** (v.421.13) — покупная десктопная программа на ноутбуке, и это не только
биддер: он агрегирует все кабинеты, к которым есть доступ, даёт аналитику и разбор
конкурентов.

Отсюда решение: **не дублировать его ни в ставках, ни в аналитике.** Свой биддер
будет драться с ним за ставки в одном кабинете. Свой сбор данных потребует токена
на каждый кабинет и даст худшую копию того, что уже куплено. Конкурентов агент
вообще не увидит — в WB API их нет.

Разделение ролей:

| Кто | Что делает | Где работает |
|---|---|---|
| Bider | ставки, аналитика по кабинетам, конкуренты | ноутбук, только когда открыт |
| Агент | надзор, сводки, алерты | сервер, круглосуточно |

Ключевая разница: **Bider показывает, когда в него смотрят. Агент приходит сам.**
Счёт в нуле два месяца — ровно эта дыра.

**Источник данных — экспорт в Excel, он в Bider есть.** Токены WB API на старте не
нужны вовсе: `scripts/bider-ingest.py` разбирает выгрузку в CSV прямо в каталог
кабинета, агент читает их как обычные файлы. Это снимает главную проблему
многокабинетной схемы — иначе токен понадобился бы на каждый клиентский кабинет,
и каждый пришлось бы выпрашивать у клиента.

API продвижения WB (категория «Продвижение») остаётся на потом — он нужен, только
если захочется, чтобы агент сам менял ставки. Пока Bider это делает, не нужен.

Ловить агент должен то, чего Bider не сообщает:

- рекламный счёт опустел или близок к нулю;
- кампании не менялись N дней — то есть биддер не работает (ноутбук выключен,
  программа закрыта, подписка истекла);
- бюджет открутился быстрее обычного;
- ДРР вышел за порог;
- дубли кампаний на одном SKU.

### Состояние на 30.08.2026 (по скриншоту Bider)

Зафиксировано как отправная точка, требует проверки в личном кабинете:

- рекламный счёт `0 ₽`, оплачено `0 ₽`;
- 51 кампания, ставки и бюджеты помечены «59 дн. назад» — около двух месяцев без
  изменений; фактически реклама простаивает;
- активной числится одна кампания («Комплект украшений», ставка 164 ₽, бюджет
  1 584 ₽), но при нулевом счёте показов нет;
- CTR, затраты и конверсии пустые — возможно, не выполнена синхронизация;
- SKU `438881147` (солнцезащитные очки) имеет две кампании, одна из них `Uni` — дубль.

Первое, что должен уметь агент, — не давать этому состоянию повториться незамеченным.

## 5. Этапы

| Этап | Что делаем | Результат |
|---|---|---|
| 0 | Поднять `nomado-market` из шаблона | Бот отвечает по экономике |
| 1 | Завести кабинеты в `core/accounts/`, заполнить ставки | Маржа считается по каждому кабинету |
| 2 | Первая выгрузка из Bider через `bider-ingest.py` | Агент работает на реальных числах |
| 3 | Занести ассортимент и стратегии | Рекомендации по цене по вашим SKU |
| 4 | Поднять `nomado-content` | Визуал, тексты, отзывы и вопросы |
| 5 | Регулярный импорт выгрузок + алерты | Сводки приходят сами |
| 6 | Решение по travel-контуру | Освобождается сервер или нет |

Развернуть воркспейсы:

```bash
./scripts/nomado-workspace-init.sh                  # экономика
./scripts/nomado-workspace-init.sh --role content   # контент
```

Загрузить выгрузку:

```bash
python3 scripts/bider-ingest.py --input export.xlsx --account own --inspect
python3 scripts/bider-ingest.py --input export.xlsx --account own
```

## 6. Допущения — поправьте, если мимо

- **Wildberries — подтверждён**: Bider работает с WB, кабинет оформлен на ИП.
  ‹уточнить› Есть ли Ozon, или пока только WB.
- **Модель — смешанная, подтверждено**: своя торговля плюс ведение клиентских
  кабинетов. ‹уточнить› Какая из двух линий главная — от этого зависит, что
  автоматизируем в первую очередь.
- ‹уточнить› Travel-контур ещё живой и его нельзя просто снести.
- ‹уточнить› Домен `nomadotravel.com` остаётся, несмотря на смену профиля.
- ‹уточнить› Налоговый режим для расчёта маржи. Кабинет на ИП, предполагаю УСН 6%,
  но это надо подтвердить — от режима зависит вся формула в `unit-economics.md`.

Ставки комиссий, логистики и хранения **намеренно не проставлены**: они меняются по
категориям и по времени, и выдуманное число в расчёте маржи хуже, чем пустое поле.
В шаблоне под них стоят явные placeholder'ы.

## 7. Чего я не видел

Эта сессия работает в одноразовом контейнере: наружу открыт только HTTPS через прокси,
SSH-ключей нет, `nomadotravel.com` заблокирован егресс-прокси. Поэтому текущий код Номадо,
содержимое серверов и живой travel-контур я не смотрел — блюпринт опирается только на
устройство `dashi-plugin-claude-code` и на ваше описание.

Чтобы снять это ограничение, есть два пути: либо выложить код Номадо в репозиторий, к
которому у меня есть доступ, либо давать мне задачи через агента, который уже живёт на lab —
у него руки на самой машине есть.
